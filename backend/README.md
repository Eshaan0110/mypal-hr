# My Pal backend

FastAPI service for the My Pal HR policy chatbot prototype. Python 3.11, managed with [uv](https://docs.astral.sh/uv/). PostgreSQL 16 runs in Docker for local development.

## Setup (from a clean checkout)

Prerequisites: uv and Docker Desktop.

```bash
cp .env.example .env          # repo root: choose a local MYPAL_DB_PASSWORD (never commit .env)
docker compose up -d          # from the repo root: starts Postgres on 127.0.0.1:5432
cd backend
uv sync                       # creates .venv with Python 3.11 and installs exactly what uv.lock lists
cp .env.example .env          # local settings; put the same password in both database URLs
uv run alembic upgrade head   # creates all tables
```

On first start, Docker also creates a separate `mypal_test` database for the test suite.

## Run

```bash
uv run uvicorn mypal.main:create_app --factory --reload
```

- Liveness: <http://127.0.0.1:8000/api/health> (process is up)
- Readiness: <http://127.0.0.1:8000/api/health/ready> (database reachable; 503 if not)
- API docs (not in production): <http://127.0.0.1:8000/api/docs>

## Test and lint

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

Database tests run against `MYPAL_TEST_DATABASE_URL` (a database whose name must end in `_test`; the suite refuses anything else because it drops all tables). Each test runs inside a transaction that is rolled back. If Postgres is not running, database tests are **skipped** with a message, not passed.

## Database migrations (Alembic)

| Task | Command |
|---|---|
| Apply all migrations | `uv run alembic upgrade head` |
| Show current revision | `uv run alembic current` |
| Create a migration after changing models | `uv run alembic revision --autogenerate -m "describe change"` |
| Check models and migrations agree | `uv run alembic check` |
| Undo the last migration | `uv run alembic downgrade -1` |

Always read an autogenerated migration before applying it. Autogenerate cannot see triggers or functions (for example the append-only audit trigger), so those are written by hand.

## Policy ingestion (development CLI)

Turns a PDF or Word policy into a **draft** version with chunks and a quality report. Nothing is published; drafts are invisible to employees until reviewed, approved and published (Phase 7). The HR admin portal will replace this CLI.

```bash
uv run mypal-ingest parse ../sample_data/policies/leave-policy-v1.pdf     # preview only, stores nothing
uv run mypal-ingest seed-demo                                             # FICTIONAL scope codes for the samples
uv run mypal-ingest ingest ../sample_data/policies/leave-policy-v1.pdf     --policy-key leave-policy --title "Leave Policy" --owner "HR Operations (fictional)"     --version v1 --uploaded-by dev-uploader@example.test --effective-from 2026-01-01     --scope "DEMO-HEALTH:*:PERMANENT" --scope "DEMO-HEALTH:*:PROBATION"
uv run mypal-ingest list                                                  # stored versions
uv run mypal-ingest show <version-id> --full                              # inspect a draft
```

`--scope` is `COMPANY[:LOCATION[:CATEGORY]]`, with `*` meaning "all"; repeat it for several. `--uploaded-by` is self-declared in this development tool; the API will take it from the logged-in identity.

What the pipeline does:

1. **File checks** — format decided from file content, not name; PDF and DOCX only; 20 MB limit; zip-bomb guard; encrypted PDFs rejected.
2. **Parsing** — headings (level from section numbering, else font size or Word heading style), paragraphs, bullet lists and tables, in reading order. PDF running headers/footers are removed. Word documents have no page numbers.
3. **Quality report** — flags pages with no text layer (likely scans needing OCR), undecodable text, missing headings and extracted tables to verify. A document with no readable text is **blocked**.
4. **Chunking** — one section never mixes with another; text packed up to ~250 words and split at sentence boundaries; tables are separate chunks, split by rows with the header repeated. Each chunk keeps its heading path, section number and page range for citations.
5. **Storage** — draft version, scopes, chunks and an audit event are written in one transaction. Duplicate files, reused version labels and unknown scope codes are rejected.

Sample policies in `../sample_data/` are **fictional**; see its README.

## Layout

| Path | Responsibility |
|---|---|
| `src/mypal/main.py` | App factory: settings, logging, database engine, middleware, error handlers, routers |
| `src/mypal/config.py` | Typed settings read from `MYPAL_*` environment variables / `.env` |
| `src/mypal/errors.py` | `AppError` and the single JSON error envelope |
| `src/mypal/api/` | HTTP routers (thin) and shared dependencies |
| `src/mypal/schemas/` | Pydantic request/response contracts |
| `src/mypal/db/` | Engine/session handling, declarative base, ORM models |
| `src/mypal/ingestion/` | File checks, PDF/DOCX parsers, quality report, chunker, draft storage, CLI |
| `src/mypal/observability/` | Request IDs and structured logging |
| `scripts/` | Development scripts (fictional sample policy generator) |
| `migrations/` | Alembic environment and migration scripts |
| `tests/` | pytest suite (`tests/db/` needs Postgres; `tests/ingestion/` builds its own PDFs and DOCX files) |

## Data model

| Table | Holds | Key rules enforced by the database |
|---|---|---|
| `companies`, `locations`, `employee_categories` | Scope reference lists | Upper-case codes; scope columns elsewhere are foreign keys to these |
| `policies` | Stable policy identity and HR owner | Unique slug key |
| `policy_versions` | Each uploaded version and its lifecycle status | One `active` version per policy; approver ≠ uploader; approved/active/superseded need an approver; reviewed states need an effective date; a replacement must belong to the same policy |
| `policy_version_scopes` | Company / location / category a version applies to (NULL = all) | No duplicate combinations |
| `chunks` | Retrievable passages with headings and page numbers | Non-blank text; valid page range |
| `faqs`, `faq_sources` | HR-approved fixed answers and the chunks they rely on | Approver ≠ author; active FAQs must be approved |
| `hr_contacts` | Designated HR contact routes (from HR, never invented) | Non-blank route |
| `feedback` | Answer ratings | Stores **no** question text, answer text or user identity |
| `query_metrics` | Per-question latency, tokens and cost | No text, no user identity |
| `audit_events` | Administrative actions | Append-only: UPDATE, DELETE and TRUNCATE are rejected by a trigger |

Lifecycle: `draft → in_review → approved → active → superseded`, or `rejected`. Actor IDs (`created_by`, `approved_by`, `actor_id`) come from the identity provider; there is no local users table.

## Conventions

- **Errors** always look like `{"error": {"code", "message", "request_id", "details?"}}`. Raise `AppError` for expected failures; unexpected exceptions return a generic 500 and are logged with a traceback.
- **Request IDs**: every response has `X-Request-ID`, and every log line made while handling it carries the same ID.
- **Settings** are only read in `config.py`; routes receive them through `SettingsDep`, and database sessions through `DbSession`.
- **Logs** never include query strings, request bodies, validation input values or database passwords.
- **Windows note**: use `127.0.0.1`, not `localhost`, in database URLs — `localhost` tries IPv6 first and stalls.
